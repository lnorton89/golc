## Phase Goal

**As an** integrator, **I want to** inspect and control every public GOLC capability through a secure, versioned, revision-aware HTTP API, **so that** external programs behave exactly like the desktop application.

<objective>
Deliver the genuinely atomic `/v1/batch` endpoint (D-15) — the phase's highest-risk design (07-RESEARCH.md Pitfall 1 / Open Question 1). Resolve the atomicity problem WITHOUT the ~15-file State-in/State-out refactor: apply the ordered sub-requests against a throwaway copy of the .golc file, then commit the aggregated final State to the real show in ONE atomic Save (or reject the whole batch, leaving the real show untouched).

Purpose: satisfies D-15's "applied as a single atomic transaction (all-or-nothing)" for the MVP while keeping internal/command's handlers unmodified — the copy-plus-single-save strategy gives true atomicity, not the weaker pre-validate-then-commit fallback.
Output: POST /v1/batch with all-or-nothing semantics, batch-level If-Match, and per-index failure reporting.
</objective>
