## Phase Goal

**As an** integrator, **I want to** inspect and control every public GOLC capability through a secure, versioned, revision-aware HTTP API, **so that** external programs behave exactly like the desktop application.

<objective>
Close verification gap 3 (API-06 / Success Criterion #4's "every result is auditable", 07-REVIEW.md WR-02): fire the post-mutation observer for every early return in `runBatch`'s pre-lock translate/scope-check loop, so a rejected batch sub-request leaves the same audit evidence the equivalent rejected single mutation already does. Fold in WR-03 in the same pass — `mutate.go`'s own scope-lookup-error branch has the identical defect one file over.

Purpose: 07-VERIFICATION.md confirmed by code trace that `POST /v1/pools` with an insufficiently-scoped key writes an audit_log row, while an identical probe through `POST /v1/batch` writes none. `TestBatchRequiresScope` only asserts the 403 and the unchanged revision, so the gap is real and untested. Rule 2 of this phase's own design ("batch must not be a scope-bypass vector") is exactly the surface being weakened.
Output: three observer calls in `runBatch`'s pre-flight loop, one in `mutate`'s scope-lookup branch, and audit assertions that pin scope rejection, translation rejection, sub-request ordering, the empty-batch semantic, and single-versus-batch parity.
</objective>

## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| authenticated client → /v1/batch pre-flight | An arbitrary ordered list of client-chosen method/resource/body triples is translated and scope-checked before any lock or copy is taken |
| mutation attempt → audit_log | The audit trail is the only durable record that an attempt occurred; a path that skips it is invisible to every later investigation |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |

| T-07-22 | Repudiation | `runBatch` pre-flight translate/scope-lookup/scope-rejection early returns | high | mitigate | Each early return fires a failure `MutationEvent` through the existing observer seam, so a scope-probing or endpoint-probing batch writes exactly one audit row — the same evidence the single-mutation path already produces. Pinned by TestBatchScopeRejectionIsAudited and the batch-versus-single parity test. |
| T-07-22b | Repudiation | `mutate`'s `requiredScopeForRoute` error branch (WR-03) | medium | mitigate | The branch now fires the observer before its 500, removing the trap that would silently un-audit the first new mutating route wired without a `domainScope` entry. |
| T-07-23 | Information Disclosure | the new failure rows carry client-supplied sub-request identity and args | medium | mitigate | Every row flows through `audit.go`'s `auditObserver`, which applies `redactArgs` plus `internal/security.Redact` before serialization; the translation-failure path records no args at all, since none were built. | T-07-24 | Denial of Service | an authenticated client can now provoke one audit row per rejected batch | medium | accept | Every /v1 request already passes `AuthMiddleware` and per-key `RateLimitMiddleware`, so audit-row insert rate is bounded by the existing rate limit; the single-mutation path has had this identical property since 07-07, and the alternative (staying silent) is the defect being fixed. |
