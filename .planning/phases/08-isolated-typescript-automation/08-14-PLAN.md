<objective>
Close 08-VERIFICATION.md's single remaining gap: the resource/memory termination cause is the only one of D-08's four causes (deadline, rate, resource, capability-scope) that does not render its Copywriting Contract sentence. A script that exhausts its Job Object memory ceiling is bounded correctly at the OS level but surfaces a raw, uncaught V8 `RangeError: Array buffer allocation failed` as `status: failed` with a stack trace as the reason, instead of 08-UI-SPEC.md:126's `"Terminated: {limit name} exceeded ({limit value}). Increase the limit in this script's profile if this is expected."`.

Per the repository owner's decision for this gap-closure run, the fix is the **proactive Go-side memory-usage monitor** — not a UI-SPEC amendment documenting the raw exception as accepted behavior.

Purpose: the memory limit is a first-class, user-assignable field in the Run/Debug dialog ("Memory limit (MB)", D-09). When a user sets it and a script hits it, the app must say so in the same named-limit voice it already uses for deadline and rate (D-08), streamed through the same live event pipeline (D-04) and terminal banner (D-12), with the first-writer-wins termination-reason discipline (D-11) preserved.

Output: a polling memory monitor bound to the run's own Job Object, a pure decision function pair that both the monitor and a post-exit classifier share, a read-only `PeakJobMemoryUsed` query on both platform builds, the session.go wiring, and the one missing `describeTermination` branch on the frontend.

**Non-goals (explicit):** this plan does not change the Job Object's memory or CPU configuration, does not add a CPU-cap termination message (the CPU cap throttles rather than kills — the deadline is what ends a CPU-bound run, and that copy already works), does not introduce any new npm or Go module dependency, and does not touch the generated SDK.

**MVP-mode note (planner-surfaced, non-blocking):** ROADMAP.md marks Phase 8 `Mode: mvp`, but (a) the phase's own goal line is not written in User Story form — the same discrepancy every prior Phase-8 plan and 08-VERIFICATION.md already surfaced and recorded as non-blocking rather than inventing a story — and (b) this is a single narrow backend-plus-copy fix for one already-shipped behavior. Per the gap-closure planning contract, that is stated here explicitly rather than forcing an artificial vertical slice: the three tasks below are dependency-ordered layers of one indivisible fix (decision logic → OS query and host wiring → rendered copy), not independently shippable user capabilities. Task 3 is the first point at which the user-visible sentence actually changes.

## Existing contract this plan extends (read before writing anything)

**`TerminationReason` (capability.go:53-65)** — `{Code string; Message string; At time.Time}`; `String()` renders `"<code>: <message>"`. This is the exact text the frontend parses. The new memory cause MUST be a `TerminationReason` of this same shape and MUST NOT introduce a second reason type.

**`checkDeadline(elapsed, deadline time.Duration) *TerminationReason` (capability.go:154-163)** — the exact shape to mirror: a pure function, nil below the boundary, a populated reason at or above it, no OS access, no logging, no side effects. `checkMemoryPressure` is its sibling.

**`(*Run).beginTermination(reason) bool` / `(*Run).terminate()` (session.go:138-184)** — the single, first-writer-wins recording path (D-11) and the CDP-bridge-then-Job-Object-then-context kill order. The monitor MUST use exactly this pair, in exactly this order, the same way `(*Host).enforce` (session.go:365-372) already does. It MUST NOT close the job handle itself, cancel the context itself, or write `run.termination` directly.

**`Run`'s post-`cmd.Wait()` branch chain (session.go:894-918)** — four ordered branches: recorded termination reason, `context.DeadlineExceeded`, other `runCtx.Err()`, then `waitErr != nil && Status == Succeeded`. The proactive monitor lands in branch 1 for free (it records a reason). The post-exit classifier extends branch 4 only. Branches 1-3 MUST NOT be reordered or edited.

**`runDispatchIO`'s stderr handling (session.go:555-570, 648-652)** — every stderr line is already `security.Redact`-ed before it reaches `stderrTail`, and `outcome.Reason` is filled from that redacted tail when nothing else set it. The classifier therefore reads an **already-redacted** string; it MUST NOT redact again (that would violate the WR-01 single-redaction-point invariant this phase's code review just restored) and MUST NOT copy any part of that string into the reason it produces.

**`windows.QueryInformationJobObject` (golang.org/x/sys v0.46.0, pinned)** — signature is `func QueryInformationJobObject(job Handle, JobObjectInformationClass int32, JobObjectInformation uintptr, JobObjectInformationLength uint32, retlen *uint32) (err error)`. Note it returns **only** `err`, unlike `SetInformationJobObject` which returns `(ret int, err error)` — the existing calls at jobobject_windows.go:103 and :120 use the two-value form; do not copy that arity for the query. `windows.JOBOBJECT_EXTENDED_LIMIT_INFORMATION` carries `JobMemoryLimit uintptr` and `PeakJobMemoryUsed uintptr`; `windows.JobObjectExtendedLimitInformation` is the information class constant (already imported and used by `newJobObject`). `PeakJobMemoryUsed` is only maintained because `JOB_OBJECT_LIMIT_JOB_MEMORY` is already set on this job, and it remains readable after the child exits for as long as the handle is open.

**`describeTermination(status, reason)` (ScriptDebugPanel.tsx:138-171)** — three regex branches (deadline / rate / scope) each returning the exact Copywriting Contract sentence, then a generic `Terminated: {reason}` fallback. The memory branch is a fourth regex branch placed alongside them. The function's own doc comment (lines 128-137) currently documents the absence of a memory signal as a known limitation and MUST be rewritten to describe the signal that now exists.

**`show.ResolvedLimits` (show/scripts.go:128-133)** — `{Deadline time.Duration; RatePerSecond, MemoryLimitMB, CPUCapPercent int}`. Presets resolve to 256 MB (quick-action, also the safe default), 512 MB (long-running), or the advanced profile's own `MemoryLimitMB` (ceiling 8192). `memoryLimitBytes(mb int) (uint64, error)` (capability.go:182-191) is the only sanctioned MB→bytes conversion and already rejects non-positive and overflowing values.
