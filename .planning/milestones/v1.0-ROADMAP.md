# Milestone v1.0: Core Lighting Console (Club/DJ)

**Status:** ✅ SHIPPED 2026-07-27
**Phases:** 1-8
**Total Plans:** 99

## Overview

v1.0 delivers the complete deterministic lighting-console core: offline-safe project
configuration and Linear traceability, a modular semantic fixture catalog with
pool/deployment impact review, tempo-aware show programming and playback that stays
deterministic under load, real Art-Net output verified against hardware, durable
SQLite-backed show storage with recovery, a full Wails desktop authoring/operator
surface with generic MIDI control, a versioned/audited external HTTP API, and
isolated, capability-limited TypeScript scripting with a real debugger. Provider-
neutral AI autonomy (Phase 9), Windows release qualification (Phase 10), and the
telemetry/crash pipeline (Phase 11) were scoped as part of the original v1
requirements set but are shipped under a later milestone — see "Scope Note" below.

## Phases

### Phase 1: Offline Foundation and Delivery Traceability

**Goal**: Contributors can configure, validate, build, and trace GOLC from durable repository-owned sources without requiring Linear or secrets to be available.
**Depends on**: Nothing (first phase)
**Plans**: 32 plans (32/32 complete)

**Details:**
Centralized, layered project configuration (committed → user → project-local →
environment → CLI) with fail-closed locked-key rejection; a durable local ID grammar
(project/milestone/phase/requirement/plan/task) that survives renames; a
credential-free, idempotent Linear reconciliation pipeline (preview → apply → resume)
proven against fixture and fake-SDK scenarios; a checksum-pinned Go/Node/Wails
bootstrap; and a self-registering command/route graph with mechanical
scope/parity gates. Closed with a two-CR gap-closure round (stale-apply resume,
uncaught SDK read failure) before LINR-03/04 were certified complete.
**Requirements:** CONF-01..04, LINR-01..04 — all Complete.

### Phase 2: Modular Fixtures and Deployments

**Goal**: Show authors can build a trustworthy semantic fixture catalog and adapt logical fixture pools to concrete deployments through explicit, atomic impact review.
**Depends on**: Phase 1
**Plans**: 6 plans (6/6 complete)

**Details:**
Canonical, versioned-schema fixture validation with actionable diagnostics; OFL
import through the same normalization/pinning pipeline as hand-authored YAML
(SSRF-guarded fetch, lossy-import warnings); content-addressed fixture identity and
provenance; logical pools mapped to concrete deployments (modes/universes/addresses)
with a deterministic, review-before-apply impact plan for every dependent group,
theme, scene, chase, and motion preset; and capability-diff fixture substitution
that never silently approximates unsupported semantics.
**Requirements:** FIXT-01..06, POOL-01..08 — all Complete.

### Phase 3: Deterministic Show Programming and Playback

**Goal**: Authors can build tempo-aware shows whose compiled playback remains deterministic without any adapter owning musical or frame time.
**Depends on**: Phase 2
**Plans**: 7 plans (7/7 complete)

**Details:**
Selection + semantic attribute programming (intensity/color/position/beam) with
touched-value/source inspection; reusable color themes, presets, tempo-relative
chases, and motion presets with full record/update/rename/reorder/duplicate/delete
CRUD and session-scoped undo/redo; bar-loop scenes with independently enabled
base-look/color-theme/chase/motion layers and fixed-priority blending; a pure
musical clock with numeric/tap BPM and preserve/restart-on-BPM-change semantics; and
an all-or-nothing compile + pure evaluate + lock-free playback engine that adopts
staged edits only at the next bar boundary, mechanically proving SCEN-09 determinism.
**Requirements:** PROG-01..07, SCEN-01..09 — all Complete.

### Phase 4: Observable Art-Net Live Output

**Goal**: Operators can drive a small Art-Net rig from deterministic complete frames and verify protocol, target, and timing health independently of the desktop UI.
**Depends on**: Phase 3
**Plans**: 9 plans (9/9 complete)

**Details:**
Byte-exact Art-Net 4 ArtDMX encoding wired end-to-end from playback frames; pinned
Windows interface selection with independent loss detection; a unicast-only target
model with fan-out, dedupe, and enable/disable; a non-blocking 40Hz ticker-driven
worker with frame/target health tracking that cannot be backpressured by UI,
storage, scripts, API, or LLM work; a long-lived headless daemon behind a Windows
named-pipe IPC boundary; a CLI operator surface; optional suggestion-only ArtPoll
discovery; and an ARTN-06 release-candidate verification pass against Wireshark, an
independent OLA simulator, and real Art-Net hardware. Two post-verification gap
closures surfaced per-universe final DMX values and pinned-interface degraded
status through `artnet status`.
**Requirements:** ARTN-01..06 — all Complete.

### Phase 5: Durable Shows and Recovery

**Goal**: Users can save, restore, migrate, recover, inspect, and export shows without storage work disturbing live output.
**Depends on**: Phase 3
**Plans**: 5 plans (5/5 complete)

**Details:**
SQLite-backed `.golc` store (WAL, synchronous=FULL) replacing JSON file I/O behind
unchanged Load/Save signatures, with an in-transaction recovery point on every save;
offer-only interrupted-session recovery (detect/accept/discard) wired into `show
open`; a verified-backup (`VACUUM INTO` + read-back-validate) migration engine using
a Go function-map registry with a Windows-safe atomic rename swap; integrity
diagnostics and versioned JSON export; and a detect-then-confirm migration flow that
refuses unsupported newer formats byte-unchanged.
**Requirements:** SHOW-01..06 — all Complete.

### Phase 6: Wails Authoring and Operator Surface

**Goal**: Authors and playback operators can complete the conventional show workflow through a responsive Wails application, keyboard, and constrained generic MIDI controls without the frontend becoming runtime authority.
**Depends on**: Phases 2, 3, 4, and 5
**Plans**: 12 plans (12/12 executed, including 4 gap-closure plans)

**Details:**
Named, individually-assigned constrained operator surfaces with per-surface MIDI
conflict rejection and server-side visible-but-locked enforcement; daemon-resident,
atomic Blackout/Stop-Release-All/Revoke-Automation/Grand-Master/group-master safety
overrides on the Art-Net worker's per-tick path, independent of UI/script/API/LLM
completion; a Wails desktop shell with OS-level safety hotkeys bypassing the
webview entirely; on-screen playback controls plus a documented, fully mirrored
keyboard workflow; a cross-to-catch soft-takeover generic MIDI Note/CC driver with
learn UI; and, via a 4-plan gap-closure round, genuine MIDI-to-action dispatch plus
on-screen fixture-patch, deployment/Art-Net-config, and scene/look-programming UI
(PLAY-10/11/12) closing the two gaps `06-VERIFICATION.md` identified.
**Requirements:** PLAY-01..12 — all Complete. (PLAY-10/11/12 were functionally
delivered and verified at gap-closure time but their REQUIREMENTS.md checkboxes
were left unflipped per `06-12-PLAN.md`'s explicit scoping choice; corrected to
Complete during v1.0 milestone archival — see Milestone Summary below.)

### Phase 7: Versioned External Control API

**Goal**: External programs can safely inspect and control every public capability through the same typed command model as the desktop application.
**Depends on**: Phase 6
**Plans**: 15 plans (15/15 complete, including 6 gap-closure plans across two rounds)

**Details:**
A Chi+Huma `/v1` HTTP server hosted inside the Art-Net daemon, translating HTTP
requests through the same internal command registry the desktop UI uses, with a
mechanical capability-coverage gate; loopback-by-default binding requiring explicit
opt-in plus interface for remote access; scoped/expiring/revocable API keys with
per-key rate limiting; a mutex-serialized mutation pipeline (If-Match/412, dry-run,
idempotency-key replay, post-mutation observer seam); atomic `/v1/batch` via a
throwaway copy-and-discard-or-commit pattern; an append-only, redacting audit log;
revisioned SSE events with Last-Event-ID replay and resync-on-gap; and a generated,
drift-checked OpenAPI 3.1 contract with a live deprecation/sunset mechanism. Two
gap-closure rounds fixed a live-reproduced SSE data-loss bug, closed audit coverage
for every batch failure branch (9/9 traced), scoped idempotency keys per-actor, and
narrowed API-01's claim to the delivered `/v1` breadth (remaining domains deferred
to `EXTN-05`, v1.x).
**Requirements:** API-01..06 — all Complete.

### Phase 8: Isolated TypeScript Automation

**Goal**: Users can create and debug typed TypeScript automation in a supervised, capability-limited process that cannot own or delay deterministic output.
**Depends on**: Phase 7
**Plans**: 13 plans (13/13 executed)

**Details:**
A Script/CapabilityProfile entity and CLI CRUD surface; a checksum-pinned Deno
toolchain resolved through exactly one function, never falling back to PATH; a
self-registering typed SDK generator producing byte-stable, drift-checked
`golc.d.ts`/runtime shim with build-breaking route-coverage parity; a Scripts
workspace (library/editor/save/delete); a zero-permission Deno host over a
multiplexed stdio session protocol; capability/rate/deadline enforcement backed by
a real Windows Job Object with kernel-enforced, uninterceptable kill-on-close; a
zero-import structural gate plus `deno check` type validation with source-mapped
diagnostics; a live, non-coalescing script event stream feeding the Phase 7 audit
trail; a real CDP breakpoint/step debugger against Deno's `--inspect-brk`, gated to
Debug mode only; Run/Debug Wails bindings with a live debug panel; a real Monaco
editor with live type-checking against the generated SDK; a breakpoint gutter and
execution-line highlight with step controls; and a final agent-executed acceptance
pass that found and fixed two real bugs (a debug-mode CDP hang and a test-hermeticity
issue) before the owner reviewed the evidence and closed the phase.
**Requirements:** SCRP-01, 02, 04, 05 — Complete at phase close. SCRP-03, SCRP-06
were functionally delivered and verified (Plans 08-05/08-06/08-07/08-13) but their
REQUIREMENTS.md checkboxes were left unflipped; corrected to Complete during v1.0
milestone archival — see Milestone Summary below.

## Milestone Summary

**Scope Note:**

ROADMAP.md and REQUIREMENTS.md originally defined "v1" as all 11 phases, including
Phase 9 (Provider-Neutral AI and Bounded Autonomy), Phase 10 (Windows Release
Qualification), and Phase 11 (Telemetry/Crash Pipeline). At milestone-close time
(2026-07-27), the repository owner decided to ship the deterministic core (Phases
1-8) as v1.0 now, narrowing the target audience to club/DJ operation (see
`PROJECT.md`), and to carry LLM-01..09, WIN-01..04, and TELE-01..04 forward into a
later milestone rather than blocking this release on them. This matches the owner
decisions already recorded in `.planning/POST-PHASE-8-PLAN.md` (2026-07-25), which
also calls for a hygiene phase and a front-door-UI completion phase before Phase 9
starts.

**Requirements Documentation Corrections:**

Two independent phase-verification reports (`06-VERIFICATION.md`, and Phase 8's
`08-13-SUMMARY.md` cross-referenced with `08-06-SUMMARY.md`) flagged that
REQUIREMENTS.md understated delivered scope:

- PLAY-10, PLAY-11, PLAY-12 (Phase 6): implemented and verified by gap-closure
  plans 06-10/06-11/06-12 (8, 5, and 7 passing tests respectively; components
  wired into the Wails shell) but left as `- [ ]`/"Pending" per an explicit,
  documented scoping choice in `06-12-PLAN.md` Task 4 that was never followed up.
- SCRP-03, SCRP-06 (Phase 8): SCRP-06 (uninterceptable kill without interrupting
  playback/Art-Net) proven by `08-06-SUMMARY.md`'s `TestScriptKillDoesNotBlockArtnet`
  and the Windows Job Object kill-on-close guarantee. SCRP-03 (no ambient
  filesystem/network/environment/subprocess/native-code access) proven by the
  zero-permission Deno host (08-05) and the zero-import gate (08-07), with
  integration coverage reconfirmed in 08-13's acceptance pass.

Both were corrected to Complete in REQUIREMENTS.md as part of this archival, with
this note as the paper trail (matching the correction pattern `06-12-PLAN.md`
already used for PLAY-01..09).

**Key Decisions:**

- Decision: Close v1.0 at Phase 8, splitting the originally-unified 11-phase "v1"
  scope. Rationale: ship the proven deterministic core now rather than block release
  on unstarted AI/Windows/telemetry work. Outcome: ✓ Good — matches owner decision
  recorded 2026-07-25 in `POST-PHASE-8-PLAN.md`.
- Decision: Narrow target audience from "clubs, churches, schools, community venues"
  to club/DJ. Rationale: church/school/community language was aspirational and never
  validated; the actual scene/BPM/layer model fits club/DJ use. Outcome: ✓ Good.
- Decision: Windows named-pipe IPC + long-lived daemon architecture for Art-Net
  (Phase 4) instead of an in-process worker. Rationale: keeps Art-Net timing
  independent of UI/CLI process lifecycle. Outcome: ✓ Good — proven under Phase 6-8
  concurrent UI/script/API load without interference.
- Decision: SQLite-backed show storage (Phase 5) instead of JSON files. Rationale:
  transactional recovery points without blocking the playback timing path. Outcome:
  ✓ Good.
- Decision: Same internal command registry drives UI, CLI, HTTP API, and TypeScript
  SDK (Phases 6-8). Rationale: prevents control-surface behavioral drift. Outcome:
  ✓ Good — proven by Phase 7's capability-coverage gate and Phase 8's SDK-parity gate.

**Issues Resolved:**

- Phase 1: stale-apply duplication (CR-01) and an uncaught Linear SDK read failure
  that could stall the shared NDJSON reader (CR-02).
- Phase 4: two post-verification gaps (missing per-universe DMX values and
  pinned-interface degraded status in `artnet status`).
- Phase 6: MIDI mappings that produced feedback but never dispatched to scene
  switches/layer toggles/master levels/safety triggers; three missing on-screen
  workflows (fixture patch, deployment/Art-Net config, scene programming).
- Phase 7: a live-reproduced SSE data-loss bug (batched mutations sharing one
  revision silently dropped replay events); unaudited batch pre-flight rejections;
  a cross-actor idempotency-key leak; a scaffolded-but-unwired deprecation
  middleware; an 8-vs-9 branch miscount in the locked-section audit-coverage gap.
- Phase 8: a debug-mode CDP hang and a test-hermeticity bug found during the final
  acceptance pass.

**Issues Deferred:**

- `MIDI-HW-02`: independent physical Windows acceptance evidence per device
  (exact hardware revision, firmware, Windows version, GOLC build) — selection is
  resolved, named compatibility/support claims are not.
- Live GUI walkthrough / copy-string audit against `08-UI-SPEC.md`'s Copywriting
  Contract for Phase 8 — deferred to the owner's own informal testing.
- `EXTN-05` (v1.x): remaining public show-domain/Art-Net-runtime API routes and the
  Wails-vs-HTTP outcome-parity check, named and deferred rather than silently
  unmapped.

**Technical Debt Incurred:**

- A rare `-race`-mode test flake (`TestMidiServiceDispatchSceneEdgeFiresPerPressNotPerMessage`,
  1 failure in 8 full-package runs, not reproduced in 10 subsequent runs) —
  consistent with known SQLite-lock contention the plan's own retry logic targets.
- `internal/trace/transport/process.go`'s `Wait()` vs. `safeFailureSummary()` data
  race, flagged in Phase 6's deferred-items and not yet fixed.
- `TestScopeLinearCatalog`/`TestScopeLinearMap` failures against the real catalog,
  same deferred-items entry.
- README/STATE.md/ROADMAP.md progress-table drift (phase-status wording, velocity
  metrics, WORKFLOW-MAP.md still describing the pre-restructure IA) — tracked as
  the "hygiene phase" in `POST-PHASE-8-PLAN.md`, not yet executed.
- Fixture Library workspace is still a `ComingSoon` stub; show open/new/switch and
  Guided First Show onboarding are not yet built — tracked as the "front-door
  workflow completion phase" in `POST-PHASE-8-PLAN.md`.
