## Phase Goal

**ROADMAP goal (verbatim):** Users can create and debug typed TypeScript automation in a supervised, capability-limited process that cannot own or delay deterministic output.

> **MVP-mode note:** see 08-01-PLAN.md's Phase Goal section.

**This plan's slice:** the phase's safety and workflow claims move from "tested" to "observed on the real platform, by a person, with the evidence written down."

<objective>
Convert Phase 8's two least-unit-testable claims into recorded human evidence: the sandbox denial surface plus Windows resource enforcement, and the complete authoring-to-debugging workflow.

Purpose: 08-RESEARCH.md's Validation Architecture explicitly names the Windows Job Object CPU/memory hard-cap behaviour and the real-debugger attach as the parts least amenable to unit testing, and the project's own MIDI-HW precedent establishes that a capability claim needs independent physical evidence before it is asserted. GOLC will eventually need to substantiate "capability-limited sandbox" to a user; this SUMMARY is that substantiation.
Output: no code — a SUMMARY carrying the observed evidence and any carried-forward backstops.
</objective>

<task type="checkpoint:human-verify" gate="blocking">
  <name>Task 1: Sandbox denial surface and Windows resource enforcement</name>
  <what-built>
Everything in plans 08-01 through 08-12: the zero-permission Deno host, the Windows Job Object CPU and memory hard caps, the wall-clock deadline, the per-run rate limiter, the host-side capability-scope check, the uninterceptable Job-Object-close kill path, and the Art-Net non-interference guarantee.

Before presenting this checkpoint, prepare (do not run yet — the human runs them) six single-file scripts saved in a scratch show, each named for what it probes:
  1. `probe-filesystem` — attempts a file read and a file write.
  2. `probe-network` — attempts an outbound HTTP request.
  3. `probe-environment` — attempts to read an environment variable.
  4. `probe-subprocess` — attempts to spawn a child process.
  5. `probe-memory` — allocates in a tight loop past the profile's memory limit.
  6. `probe-cpu` — spins in a tight CPU loop with no allocation, with a short deadline.

Also prepare a `probe-scope` script assigned the `playback` capability scope that calls an `authoring`-scoped SDK method.

Print the full backstop inventory gathered from every 08-XX-SUMMARY.md so the human can see what is still unobserved.
  </what-built>
  <how-to-verify>
Run on real Windows hardware, with Art-Net output live to a real or loopback target throughout.

1. Run each of `probe-filesystem`, `probe-network`, `probe-environment`, and `probe-subprocess`. For each: confirm the operation is **denied**, and confirm the denial is **visible** in the debug panel as a diagnostic — not a silent no-op and not a hang.
2. Run `probe-memory` with a small memory limit. Confirm it is terminated and the banner reads the limit-exceeded copy naming the memory limit and its value.
3. Run `probe-cpu` with a low CPU cap and a short deadline. Confirm Task Manager shows the process pinned at roughly the configured cap rather than saturating a core, and confirm it is then terminated by the deadline with the deadline reason. (The CPU cap throttles; the deadline is what kills — confirm both halves.)
4. Run `probe-scope`. Confirm the run terminates with the scope-violation copy naming the attempted command and the assigned scope.
5. Throughout steps 2-4, watch the Art-Net output and the Output → Art-Net workspace. Confirm no visible interruption, no frame stall, and no status change on any target.
6. While `probe-cpu` is running, press **Stop Script**. Confirm it stops in a single click with no confirmation gesture, that playback and Art-Net are unaffected, and that the global Revoke Automation and Blackout controls were not triggered.
7. After every termination above, confirm nothing restarts on its own: leave the app idle for a minute and confirm the run stays terminated and the banner still says the script will not restart automatically.
8. Start a plain **Run** of any script and confirm no inspector or debug-protocol channel is open — for example, confirm the app's process holds no unexpected listening socket while a plain Run is in flight.
  </how-to-verify>

<task type="checkpoint:human-verify" gate="blocking">
  <name>Task 2: Full authoring-to-debugging workflow acceptance</name>
  <what-built>
The complete SCRP-01 through SCRP-06 surface: the Scripts library, the Monaco editor with live type-checking and autocomplete against the generated SDK, validation, Run and Debug launch with the capability-profile dialog, live logs and per-call command outcomes, the persistent stopped banner, and the breakpoint/step debugger.

Before presenting this checkpoint, confirm the automated gates are green and print their output: `mage Test` and `npm --prefix frontend run build`.
  </what-built>
  <how-to-verify>
Run on real Windows hardware in the packaged or `mage Run` desktop app.

1. Open **Build → Scripts** on a show with no scripts. Confirm the "No scripts yet" empty state and the "New Script" action.
2. Create a script. Confirm it appears in the library with its name, a never-run status, and its capability-profile summary.
3. In the editor, type `golc.` and confirm real GOLC capabilities are offered by autocomplete. Confirm `playback evaluate` and any raw-DMX capability are **not** offered.
4. Introduce a wrong argument type and confirm it is underlined live, without pressing Validate.
5. Press **Validate**. Confirm the "{N} error(s)" summary appears and Run and Debug are disabled until it passes.
6. Add an `import` line and press Validate. Confirm it is rejected with an import-forbidden diagnostic on the correct line. Remove it.
7. Write a script that makes several SDK calls with a short sleep between them. Press **Run**. In the dialog, confirm the capability scope, the resource preset, and (under Advanced) the four numeric fields are all pre-filled from the saved profile and none is blank. Change the preset, then launch.
8. While it runs, confirm log lines and individual command outcomes appear **live**, in order, each formatted per the outcome copy, and confirm the show actually changed as the script instructed.
9. Press **Stop Script** mid-run. Confirm the "Stopping — finishing in-flight commands…" transient copy, then the persistent "Stopped: {reason}" banner with Dismiss and Run Again and the no-auto-restart line. Confirm the previous logs are still visible.
10. Press **Run Again**. Confirm the launch dialog re-opens (rather than launching directly) with the profile you edited in step 7 now saved as the default.
11. Click the editor gutter on a line to set a breakpoint. Confirm a red dot appears. Press **Debug**.
12. Confirm execution pauses on that line, the panel shows "Paused at breakpoint — line {N}", the editor highlights that line, and the four step controls appear. Step Over twice, Step Into once, then Continue.
13. Make the script throw. Debug again and confirm the crash renders "Script crashed: {summary}" with an expandable, source-mapped stack trace whose line numbers match your source. Click a frame and confirm the cursor moves there.
14. Resize the window narrow and confirm the library, editor, and debug panel each scroll inside their own bounded region rather than growing the page.
15. Switch the OS colour scheme and confirm the editor's theme follows.
16. Review the carried-forward backstop list from Task 1 and mark each as observed-and-resolved or explicitly carried forward with a note.
