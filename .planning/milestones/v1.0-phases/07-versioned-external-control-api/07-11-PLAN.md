## Phase Goal

**As an** integrator, **I want to** inspect and control every public GOLC capability through a secure, versioned, revision-aware HTTP API, **so that** external programs behave exactly like the desktop application.

<objective>
Close verification gap 2 (API-03 / Success Criterion #3, 07-REVIEW.md CR-01): decouple the SSE event id and the replay-buffer ordering key from `show.State.Revision`, so a multi-sub-request atomic batch's N events — which all legitimately share one committed revision (D-15) — stay individually addressable for `Last-Event-ID` replay.

Purpose: 07-VERIFICATION.md reproduced this live. A 3-sub-request `/v1/batch` publishes 3 SSE frames all tagged `id: N`; a client that saw only the first and reconnects with `Last-Event-ID: N` is told "already caught up" — no replay, no resync — silently losing the rest. That directly falsifies the package's own documented D-10 "never a silently missing gap" guarantee, for a code path that ships today.
Output: a strictly monotonic per-process event sequence used for the SSE `id:` line and for replay/resync comparisons, `Revision` retained in the payload body for domain use, a regression test combining a live SSE subscriber with a multi-sub-request batch and a reconnect, and a regenerated, drift-clean published contract.
</objective>

## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| authenticated client → SSE replay buffer | The client supplies `Last-Event-ID`, an untrusted integer that selects what the server replays |
| server event sequence → client's notion of "I have seen everything" | The id the server issues is the sole basis on which a client concludes it has no gap; a wrong answer here is a silent correctness failure, not a visible error |
